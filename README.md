# Controlled external test publisher

This is a deployable fallback for the first publisher pilot. It is **operator controlled**, not a legitimate outside publisher relationship. No deployment, outside-host verification, or new payment is established by these files or their offline tests. The earlier Arithmetic fixture is not used here.

The standalone container contains only this small FastAPI text-metrics service. It receives no marketplace database, buyer API keys, Helius credentials or wallet secrets. One POST to `/v1/text-metrics` counts characters, whitespace-separated words and `splitlines()` lines and returns a SHA-256 of the UTF-8 text. Use synthetic test strings only. Maximum input is 1,024 characters/16 KiB per request, eight concurrent streams, two seconds to read a body, one process, and 1,000 successful receipts. There are no retries or artificial failure/admin endpoints.

## Prepared deployment boundary

Build from this directory: `docker build -t aa-controlled-publisher:pilot .`.

Run on a **separate, authorized external host** behind its own HTTPS termination. It must not share the Activity Accounts gateway, production origin or database. Allocate at most one worker, 256 MiB RAM, one CPU and a small private writable `/data` volume owned by UID 10001; use a read-only root filesystem, drop all capabilities and enable `no-new-privileges`. Deny outbound networking; the API needs none. Disable reverse-proxy access logs and any request/body capture. Mount only the receipt volume. The host must expose a canonical public DNS hostname on HTTPS port 443 with a valid certificate. No production DNS change is required.

Supply environment variables through the host's private configuration interface:

- `AA_EXTERNAL_HOSTNAME`: the public DNS hostname, without scheme or path.
- `AA_EXTERNAL_CHALLENGE`: the exact 32-character public ownership challenge from the submitted listing. This value is intentionally served publicly and is not a wallet/provider secret. An initial 32-character placeholder can be replaced after submission, then the service restarted by its operator.
- `AA_EXTERNAL_RECEIPTS_DB`: `/data/receipts.sqlite` in the container.
- `AA_EXTERNAL_SYNTHETIC_RECEIPT_LOG`: optional, disabled by default. Only the exact value `1` enables one bounded hash-only JSON receipt line on stdout after each successful SQLite commit. Enable solely for the explicitly authorized synthetic qualification; no raw input, credentials, IP addresses or request metadata are logged. An unavailable log sink does not turn an otherwise successful API response into a failed request.

No hosting provider has been selected or provisioned. Prefer an already authorized independent development host with zero incremental cost; otherwise obtain approval for a specifically verified ongoing free plan with hard spending disabled. Do not use a trial requiring upgrade, purchase credits, provide a payment method or reuse the existing production server. A local process with a second tunnel does not establish independent hosting.

One candidate for a separately approved disposable deployment is a **Render Free web service**, using its Docker runtime, this directory as its build context, one Free instance, `/health` as its health check, and the environment variables above. Disable automatic deploys and select **Free** explicitly; do not select a paid instance or disk, add a payment method, or enable an upgrade. Public source publication, connecting an account/repository, and creating the service still require approval; no Render account or resource was created for this artifact. The [official Free service limitations](https://render.com/docs/free) describe 750 shared instance hours per workspace/month, spin-down after 15 minutes without traffic, an ephemeral filesystem, and no SSH or Dashboard Shell. Therefore the local SQLite receipt command below cannot be used on that plan. For the separately authorized synthetic test, explicitly enable `AA_EXTERNAL_SYNTHETIC_RECEIPT_LOG=1` and have the signed-in service operator retrieve the matching `controlled.synthetic_receipt` JSON line from the service's log view immediately after the request, before an idle shutdown, restart or redeploy. Preserve only that approved sanitized record in pilot evidence; do not export the whole log stream. Missing receipt delivery or retrieval leaves publisher confirmation unresolved. The ephemeral database is not durable evidence. Cold-start time can exceed the gateway deadline, so warm the public health check before the authorized review and purchase. Free quotas, log access/retention and platform logging/resource controls must be checked in the actual account before deployment; this remains a hosting proposal, not a verified running endpoint.

## Marketplace handoff

1. Generate the supported submission JSON locally using `python -m marketplace.external_test.contract PUBLIC_HOSTNAME` from the repository root. The generated profile is explicitly labeled **CONTROLLED EXTERNAL TEST**, and its plan is 1 Devnet USDC for five calls over 24 hours. It contains no credentials. Paste the OpenAPI document, sample and plan into the publisher draft form.
2. The publisher profile requires manual identity approval. Verify the controlled payout wallet using the existing wallet-proof workflow with separate human signature approval. Submit the draft; copy its ownership challenge into the external service configuration. `/.well-known/activityaccounts-marketplace` must return exactly `{"challenge":"<challenge>"}`.
3. A marketplace administrator reviews the submitted snapshot. The existing public-only pinned HTTPS transport must independently fetch that challenge and execute the approved sample `{ "text": "Hello pilot" }`. Do not bypass destination checks or replace this live review with a fixture.
4. Only after approval, create the buyer's 1-USDC Devnet order and obtain manual wallet approval. Confirm final settlement independently through official Solana and Helius, then make exactly one authenticated gateway request using a distinct synthetic string such as `Buyer qualification 2026-11-20` to distinguish it from the review sample.
5. The external host operator retrieves the corresponding local publisher receipt and confirms its request/response hashes and timestamp. Compare the gateway usage receipt, exactly one entitlement, five-to-four quota change, 900,000 publisher units and 100,000 platform units. Do not treat a receipt alone as proof of gateway forwarding or blockchain settlement.

## Publisher receipt confirmation

Each successful API call atomically appends a private SQLite row **before** HTTP 200: integer receipt ID, UTC epoch timestamp, operation, canonical request SHA-256, canonical response SHA-256 and status. No raw text, passwords, headers, API keys, IP addresses or user agents are stored. Canonical JSON uses sorted keys, UTF-8, no ASCII escaping and separators `,`/`:`. Hashes can reveal low-entropy synthetic text; they are for this controlled pilot only. The public response header `X-Controlled-Publisher-Receipt` gives the ID to direct callers; gateway passthrough does not promise to expose it. This public synthetic API does not authenticate the gateway as its caller: correlate a unique agreed test string and time with both ledgers, and do not claim cryptographic source attribution from a hash-only receipt.

On a host with authorized local command access, `python -m external_test.receipts /data/receipts.sqlite REQUEST_SHA256 --after 0` returns at most 100 matching hash-only records. This is a local operator command, not a network administration endpoint; it is unavailable on Render Free. The opt-in log line contains the same committed receipt fields plus the fixed event name. It has no cryptographic caller-authentication claim. Export only the matching synthetic qualification receipt after authorization; do not upload the database. At the 1,000-row cap the API returns 503 rather than silently dropping evidence. The operator must preserve/export approved evidence before rotating to a fresh disposable database.

## Remaining acceptance gates

An authorized independent host and its HTTPS URL, deployment approval/configuration, payout-wallet signature, live ownership/sample review, a fresh manually approved Devnet purchase, and publisher-side receipt retrieval remain required. A real outside publisher remains unresolved even if this controlled fallback completes. Docker image build and external TLS/resource/network controls require verification on the selected host; offline unit tests do not establish them.
